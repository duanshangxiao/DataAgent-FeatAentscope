# 知识配置最佳实践

DataAgent 通过语义模型、业务知识和 Agent 知识三类配置补充数据库元数据与业务语义。三者服务于不同问题，不应互相替代。

## 1. 三类知识的边界

| 类型 | 解决的问题 | 典型内容 |
|---|---|---|
| 语义模型 | 业务语言如何映射到具体表和字段 | 字段业务名、同义词、枚举含义、关系提示 |
| 业务知识 | 某个业务术语或口径是什么意思 | GMV 定义、有效订单条件、客户分层规则 |
| Agent 知识 | 回答问题还需要哪些非结构化背景 | SOP、FAQ、制度、行业说明、分析范例 |

知识配置不能替代数据库权限、允许表/字段范围和 SQL Guard。Prompt 或召回文本提供语义，服务端安全约束负责阻止越权和危险 SQL。

## 2. 语义模型

语义模型把用户语言映射到物理字段。只为含义不直观、容易混淆或需要业务解释的字段配置，不要求机械录入每个表和每一列。

推荐内容：

- `tableName/columnName` 与数据库物理名称完全一致。
- `businessName` 使用业务人员日常使用的标准名称。
- `synonyms` 只写真实同义表达，避免堆入泛词。
- `businessDescription` 解释枚举值、单位、时区、空值和常用过滤条件。
- `dataType` 与真实数据库一致。
- 仅启用已经验证并属于当前 Agent 数据源范围的条目。

示例：

```text
columnName: order_status
businessName: 订单状态
synonyms: 支付状态,交易状态
businessDescription: 0=待支付，1=已支付，2=已取消；计算成交订单时只包含状态1。
```

不要在一个字段描述里塞入跨表的大段计算公式；这类内容更适合业务知识。

## 3. 业务知识

业务知识用于定义术语、计算口径和组织内部规则，典型场景包括：

- 指标公式和过滤条件。
- “活跃用户”“高价值客户”等分类标准。
- 退款、撤销、内部单等特殊排除规则。
- 业务缩写、别名和内部常用称谓。

推荐写法：

```text
业务术语：GMV
同义词：交易额,成交总额
描述：统计已支付和已发货订单的下单金额总和；排除测试订单；退款金额不在本口径中扣除。
```

描述应包含边界条件，不能只写“GMV 是商品交易总额”。如果条目不希望进入运行时召回，应关闭 `isRecall`；修改召回状态或正文后要确认向量索引状态已经更新。

## 4. Agent 知识

Agent 知识用于补充非结构化背景。当前常见类型包括文档、QA 和 FAQ。

适合放入：

- 数据口径说明和组织制度。
- 固定分析流程或 SOP。
- 常见问题及经审核的答案。
- 业务场景解释、地区划分、产品分类等背景。

不适合放入：

- 数据库密码、模型密钥和个人敏感信息。
- 需要严格实时一致的事实数据。
- 大量互相冲突、没有生效日期的旧制度。
- 用来绕过 SQL 安全或权限控制的指令。

QA/FAQ 应提供可复用的业务判断或输出期望。SQL 示例只能作为参考，实际运行仍必须经过当前表范围和 SQL Guard 校验。

## 5. 当前运行时如何使用知识

当前对话主链路不是旧的 StateGraph `EvidenceNode/PlannerNode/SQLGenerateNode` 流水线。AgentScope `ReActAgent` 根据运行时装配的工具主动获取所需信息：

1. capability routing 先确定数据库或指标相关工具范围。
2. 数据源探索工具读取允许访问的表、字段和样例。
3. 语义模型搜索工具按 Agent、数据源和表范围检索字段语义。
4. 领域知识工具检索 `businessKnowledge` 与 `agentKnowledge`，可按 DOCUMENT、QA、FAQ 缩小范围。
5. Agent 综合工具结果生成 SQL 或指标请求。
6. SQL 进入服务端校验和只读执行，工具轨迹进入实时 SSE 与回答解释。

知识是否被使用取决于 Agent 工具选择、索引状态和检索命中，不是保存一条配置就一定进入每次 Prompt。

## 6. 配置与验证流程

建议按以下顺序配置：

1. 先限制 Agent 可访问的数据源、表和字段。
2. 用真实业务问题验证数据库元数据是否足够清晰。
3. 对含义模糊的字段增加语义模型。
4. 对跨字段口径和术语增加业务知识。
5. 对 SOP、FAQ 和背景材料增加 Agent 知识。
6. 等待或触发向量索引完成，检查 `embeddingStatus` 和错误信息。
7. 使用固定问题集验证召回、工具顺序、SQL、结果和报告。
8. 刷新页面，确认配置与历史回答可以正确回填。

验证时不要只看最终答案。回答 explain 和后端日志应能帮助判断：

- 是否调用了正确的语义/知识工具。
- 命中了哪类知识和哪些条目。
- 未命中是因为 `isRecall`、类型过滤、索引失败、阈值还是查询表达。
- SQL 是否真实使用了召回的口径，而不是模型自行猜测。

## 7. 常见问题

### 配了知识但没有命中

检查 Agent 归属、`isRecall`、embedding 状态、知识类型、索引中是否存在对应文档，以及问题表达与条目内容是否足够接近。

### 命中过多无关知识

收紧同义词和正文，拆分过长条目，避免一个条目覆盖多个无关主题，并用明确的知识类型过滤。

### SQL 仍然使用错误字段

优先检查数据源范围和语义模型的物理字段映射；业务知识只能解释口径，不能修复错误的表字段绑定。

### 新旧规则冲突

知识正文中写明适用范围和生效时间，停用旧条目。不要依赖模型自行判断两套冲突制度哪一套更新。

## 8. 完成检查

- 物理表、字段和数据类型准确。
- 同义词没有使用过宽泛词。
- 业务口径包含过滤条件、单位和时间边界。
- 知识不包含密钥和敏感数据。
- `isRecall` 与 embedding 状态符合预期。
- 固定问题集能够稳定命中正确条目。
- SQL Guard、允许表和字段限制仍然生效。
- 实时回答与刷新后的历史展示一致。
